The vision of the FDO concept is to enable machine actionability and the automated processing of data. If an FDO client finds a PID that identifies an FDO, then this client would be able to automatically interpret and process the FDO (subject to potential access constraints), regardless of the technology used to implement it. The basis for enabling automated processing regardless of the used technology is that FDO implementations comply with the rules specified in this implementation-agnostic specification. At its core, this specification describes the structure of an FDO - that is, the components an FDO consists of and the rules that apply to those components (Section 3). This document also details how the individual components would be found, accessed and interpreted by an FDO client, to enable automated processing of the entire FDO, especially its data (Section 4).

The FDO Building Blocks

An FDO consists of the following components (see also [[[#fig1]]]):

  • Resource: Each FDO is a standardised and persistent bundle of information that represents (i.e., identifies, encapsulates and describes) a resource. The resource could be digital, in which case the resource would usually be a data bit-sequence. But it is also possible that this resource is physical, in which case the bit-sequence could vary greatly in purpose such as representing location information, a scanned representation, a service access point or any other useful information to describe this object. The resource is the heart of the FDO and all other components are there to make the resource and its metadata machine actionable.
  • Persistent identifier (PID): Each FDO is identified by a globally unique and persistent identifier. A PID system must resolve the PID to an FDO record.
  • FDO record: The FDO record is a predictable and machine actionable information structure that contains FDO attributes describing the resource the FDO represents. The FDO record is that piece of information a FDO client first encounters after PID resolution. It is the FDO's metadata.
  • FDO attribute: The FDO Attribute is expressed a tuples (Can be though as as a type:value pair).
    1. the first element of the tuple identifies an FDO attribute definition (which is similar to the definition of a metadata field in a metadata schema), and
    2. the second element is a value instantiating this FDO attribute definition (similar to the value that is filled into the metadata field).
    An FDO attribute is a property that can be used to describe a resource, as well as the FDO itself. We distinguish three types of FDO attributes/attribute definitions:
    1. Mandatory FDO Attributes. These are core FDO Attributes specified and maintained by the FDO Forum. They are formally defined and registered as FDOs. The current attributes consists of the following three attributes: The FDO type (0.FDO/Type), the FDO profile (0.FDO/Profile) and the data of an FDO (0.FDO/Data). They ensure core FDO interoperability, predictability and machine actionability of the FDO.
    2. Optional FDO Attributes. A list of frequently used FDO Attributes. They are formally defined and registered as FDOs and will be managed by the FDO Forum. They are recommended to be used by any FDO creator to facilitate reusability and interoperability of their FDO accross various implemenations.
    3. Community-defined FDO Attributes Communities of practice are free to choose their own however, they need to ensure that they are defined and registered in open registries, preferably as FDOs.
  • FDO attribute definitions: An FDO attribute definition specifies syntactic rules and a semantic meaning of an FDO attribute. In detail, an attribute definition specifies:
    1. a label for the attribute (e.g., “Author”),
    2. a semantic description of the attribute (e.g., “Person who wrote the document”),
    3. a cardinality (e.g., this attribute can be used at most one time in an FDO record), and
    4. syntactic rules for the value that instantiates this attribute (e.g., “a string that is at most 100 characters long”).
    Attribute definitions ensure that the attributes in the FDO record are machine interpretable. They also enable validation, i.e., to check that the values of attributes follow the syntactic rules specified in the attribute definitions. Each attribute definition is itself an FDO.
  • FDO profiles: The FDO profile specifies the set of FDO attribute definitions that must or can (depending on the cardinality of the attribute definitions) be instantiated to create FDO records by a certain repository, community, or implementation. The FDO profile makes the content of an FDO record predictable for an FDO client: Each FDO record needs to have a reference to the FDO profile it complies with. By inspecting the profile, a client learns which attributes it can expect to find in the FDO record. Each FDO profile is itself an FDO.
  • FDO type: Each FDO has to specify an FDO Type which essentially provides any client with a hint how the resource can be processed.
  • FDO Registries: FDO Attribute and FDO profiles definitions must be stored in open FDO registries. An FDO Registry is a registry that stores and provides reverse lookup on FDOs and their respective attributes. The mandatory and optional FDO attribute definitions should be stored in FDO registries maintained by the FDO Forum. Communities of practice maintain their own community-defined FDO compatible attribute definitions in their open FDO compatible registries.
