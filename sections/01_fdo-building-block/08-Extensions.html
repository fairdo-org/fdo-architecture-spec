Extensions

This section is normative.

Concepts and mechanisms that are part of this section are not essential for the basic functionality of FDOs but provide additional features that can be used to extend the capabilities of FDOs. Thus, clients and FDO implementations (that follow section ) MAY choose to support these features, but they are not required to do so.

[R-Ext-1] Inline FDOs

If an attribute definition uses the profile referencing mechanism, the value of an instantiating attribute is a reference to another FDO. However, rather than providing a reference to the other FDO, it may be serialized directly as the in-line value of the instantiating attribute. In this case, the serialization depends on the implementation, and the implementation MUST specify the serialization format, if it decides to support this feature. Furthermore, inline FDOs typically do NOT have their own PIDs and are hence NOT suited to define attribute definitions or profile.

[R-Ext-2] External Vocabulary Referencing

In some cases, it will be useful to reuse existing vocabularies, ontologies, and terminologies in FDO records, e.g. to add existing specific metadata (even if vocabulary terms do not fulfill the same guarantees as attribute definitions). Using a vocabulary term as an attribute in an FDO record similar to an attribute definition is explicitly supported as a community attribute. Vocabulary terms can also be used as the value of an attribute in an FDO record. Both variants can be realized by applying the external vocabulary referencing mechanism, which is specified in the following. If implementing this mechanism is not necessary or not desired, implementations SHOULD state and explain their decision when writing their implementation profile.

The vocabulary definition profile (0.FDO/VocabularyDef) specifies which information is needed to describe a vocabulary. FDOs instantiating this profile MUST define values for the 0.FDO/Name, and 0.FDO/VocabularyPrefix attributes.

To enable automatic validation of vocabulary terms, the FDO SHOULD also specify how the vocabulary can be retrieved (using 0.FDO/Data), the format in which the vocabulary is provided (0.FDO/VocabularyFormat), and a SPARQL query that checks the validity of the vocabulary term (0.FDO/SPARQL_Check). This information (together with 0.FDO/Data) SHOULD be sufficient to download the vocabulary, import it into a client, and automatically validate the usage of terms from this vocabulary using the provided SPARQL query. If these attributes are not provided, a client MAY still use the vocabulary terms in an FDO record, but it cannot automatically validate the usage of these terms.

Optionally, 0.FDO/Description, 0.FDO/Contact, 0.FDO/LandingPage, and other attributes MAY be used to provide additional information about the vocabulary.

Using vocabulary terms similar to Attributes in FDO records

To use external vocabulary terms as attribute definitions in an FDO record, the record MUST contain the 0.FDO/ImportVocabulary attribute. Values of the 0.FDO/ImportVocabulary attribute MUST refer to an FDO that instantiates the profile 0.FDO/VocabularyDef. This attribute indicates to a client which vocabularies are used in an FDO, allowing a client to automatically detect and resolve vocabulary terms in an FDO using the prefixes specified by the vocabulary definition. The 0.FDO/ImportVocabulary attribute MAY be used multiple times in an FDO record to import multiple vocabularies. The creator of an FDO record MUST ensure that the prefixes of the imported vocabularies are unique. This mechanism validates the left side of an FDO record if the necessary attributes for validation according to are provided. It DOES NOT validate the right side of an FDO record if a vocabulary term is used as a value of an attribute (see ).
shows how schema.org terms can be used in an FDO record similar to an attribute definition by applying external vocabulary referencing (see ).
  • The attribute definition 0.FDO/ImportVocabulary accepts profile references to FDOs that instantiate the profile 0.FDO/VocabularyDef. This means that 0.FDO/ImportVocabulary indicates to a client which vocabularies are used in an FDO.
  • The profile 0.FDO/VocabularyDef specifies which information is needed to describe a vocabulary. This information must provide meaningful information of the vocabulary and should allow a client to automatically validate the usage of terms from this vocabulary. It must also enable a client to automatically detect the use of vocabulary terms in an FDO using a prefix. The reason why validation is not mandatory is that some vocabularies may not provide a machine-readable version of the vocabulary in one of the pre-defined file formats (e.g., RDF/XML, TTL, N-Quads, or JSON-LD). A fixed list of such file formats is needed for implementation.
  • 21.example/SchemaOrg uses the 0.FDO/VocabularyDef profile to describe the schema.org vocabulary. This FDO contains some metadata about the schema.org vocabulary, such as its name, description, and a URL to a landing page. It also specifies the prefixes that can be used to reference schema.org terms in an FDO, enabling clients to determine to which (if any) vocabulary a term belongs (in this case schema: and https://schema.org/). To enable automatic validation of schema.org terms, the FDO 21.example/SchemaOrg also specifies how the schema.org vocabulary can be retrieved (using 0.FDO/Data) the format in which the vocabulary is provided (0.FDO/VocabularyFormat), and a SPARQL query that is executed on the downloaded vocabulary with the $TERM$ argument to determine if the term is included in the vocabulary.
  • The FDO 21.123/example4 contains the attribute (0.FDO/ImportVocabulary, 21.example/SchemaOrg) to indicate that it uses the schema.org vocabulary described in 21.example/SchemaOrg. Afterward, any schema.org term can be used as an attribute in the form (<prefix + term>, <value>), such as (https://schema.org/priceCurrency, USD). A client automatically detects that e.g., https://schema.org/priceCurrency is a schema.org term because it starts with the prefix https://schema.org/, which is specified in the FDO 21.example/SchemaOrg.

Defining the value space of an Attribute using External Vocabularies

Attribute definitions MAY use external vocabulary referencing to define the value space of an attribute in an FDO record. This is useful if the value space of an attribute is already defined in an external vocabulary, ontology, or terminology and references to terms in those systems should be validated. If an attribute definition A uses external vocabulary referencing to define its value space, it MUST explicitly state so by instantiating the 0.FDO/AttributeDefVocabularyRef profile. External vocabulary referencing is an attribute validation mechanism and as such, 0.FDO/AttributeDefVocabularyRef extends the attribute definition profile. A MUST use the 0.FDO/ImportVocabulary attribute of A to refer to an FDO that instantiates the profile 0.FDO/VocabularyDef. This validation mechanism validates the right side of an FDO record if the necessary attributes for validation according to are provided.

External vocabulary referencing can also be used to reference a term from an external vocabulary as the value of an attribute (see ). In this case, the attribute definition that applies external vocabulary referencing refers to an FDO that instantiates the 0.FDO/VocabularyDef profile. The value of the attribute is then a reference to a term in this vocabulary.

This example shows how the attribute definition 21.example/TypeOfWork uses external vocabulary referencing. It refers to the FDO 21.example/SchemaOrgCreativeWork, which instantiates the profile definition 0.FDO/VocabularyDef and validates that the term is a subclass of CreativeWork. Creating 21.example/SchemaOrgCreativeWork is necessary to express and validate the constraint to only subclasses of CreativeWork. The attribute (21.example/TypeOfWork, schema:Photograph) in the FDO record 21.123/example5 is valid because the term https://schema.org/Photograph is a subclass of CreativeWork.
