FDO Types

Typing is an essential building block of the FDO architecture. The term “type/typing” refers to several concepts simultaneously:

  1. Attribute definitions are types for properties of an FDO and are instantiated by attributes in the FDO record.
  2. The value of the 0.FDO/Type attribute in the FDO record is a type of the resource being represented by the FDO.
  3. The value of the 0.FDO/Profile attribute in the FDO record is a type of the FDO record, which instantiates the profile.
All these types together form the type system.

FDO_Type Attribute

This section specifies the FDO type (0.FDO/Type) as the value of the 0.FDO/Type attribute, which must be (c.f. ) instantiated in FDO records. It can be repeated multiple times.
This 0.FDO/Type attribute is an intentionally chosen entry point that signals some default processing semantics for the FDO. It gives a hint to a machine how this object may be processed. Other facets of the FDO type could be derived independently of the 0.FDO/Type attribute using other typing mechanisms, e.g., by inspecting the presence of other record attributes. Please note that we will refer to the 0.FDO/Type attribute as the “FDO type” in the following.

FDO Type System

Profiles and attribute definitions are special FDOs in the sense that they are part of the FDO type system. All of these FDOs do not have a data bit-sequence they refer to, since they consist of only meta-information in the FDO record. Hence, the FDO record itself is treated as the data bit-sequence of these FDOs. This makes the profile of the FDO effectively the type of the FDO because the profile fully describes the structure of the record.
Consequently, for all profiles and attribute definitions, the 0.FDO/Type attribute MUST have at least the value 0.FDO/Profile, as it points to the profile using attribute referencing. Adding additional FDO types to these FDOs is allowed. All profiles and attribute definitions are listed in .

Communitiy-Defined FDO Types

Communities of practice may define their FDO types in accordance with their needs, whilst taking the following requirements into account:

[R-TYP-1] Type Interpretability

The FDO type SHOULD be interpretable outside the community of practice to ensure interoperability. This SHOULD be ensured by linking to existing standards or software that explain how to interpret the FDO type. These external resources SHOULD be publicly accessible.

[R-TYP-2] Type as FDO

Community-defined FDO types SHOULD be FDOs for better interpretability.

[R-TYP-3] Type Derivation

Types MAY be derived from other types (i.e., there MAY be hierarchies of types defined within communities of practice). To state that a type t2 is derived from a type t1, the FDO record of t2 SHOULD contain the attribute 0.FDO/DerivedFromType, whose value is a PID that resolves to t1.

FDO Type of Collections

FDOs may represent collections of objects (see also ). To assign FDO types to a collection and to objects within the collection, the following conditions apply:

[R-TYP-4] Collection Type

The FDO type(s) of a collection MUST describe the collection as a whole.

[R-TYP-5] Object Type in a Collection

If an FDO type SHOULD be assigned to objects within the collection, each object MUST be represented as an FDO (or inline FDO) itself. This FDO can then contain the 0.FDO/Type attribute to specify FDO types.

Operation Association Mechanisms

Types MAY be used to associate FDOs with operations. The specification of FDO operations is still in an early state and not yet completely understood. A more comprehensive list of requirements beyond – will be included in a later version of this document. However, the specification of how to associate FDO operations with FDOs which they are able to act on is already more elaborate.

[R-OPS-1] FDO Operation Definition

FDO operations (short: operations) are procedures that can be invoked on FDOs to create, manipulate or delete FDO record(s), bit-sequence(s), or trigger other related activities.

[R-OPS-2] Operation Interface

Operations abstract and encapsulate their concrete implementation details by providing a uniform interface that at least defines their input parameters, output parameters, and how the operation SHOULD be executed. This enables execution of operations in arbitrary, possibly restricted environments.

[R-OPS-3] Operations as FDOs

Operations MUST themselves be represented as FDOs. Hence, they are identified by a PID that resolves into an FDO record consisting of attributes.

[R-OPS-4] Operation Definition Profile

An operation definition profile 0.FDO/OperationDef which specifies a minimal set of attributes that an operation MUST defines does not exist yet but may be specified in the future.

[R10-14] Operation Association

To associate an operation with an FDO, types SHOULD be used (i.e., FDO attribute(s), FDO Profile(s) and the FDO type(s) as defined in ). In detail, to associate an operation with an FDO, (at least) one of the following operation association mechanisms SHOULD be applied:
  • The FDO record refers to applicable operations for this FDO via a designated attribute.
  • The FDO profile refers to applicable operations for any FDO complying to this profile via a designated attribute.
  • The attributes available in an FDO record are matched with applicable operations and the attributes they require.
More information on the operation association mechanisms is available in the paper [[FDO-Operations]].

[R10-15] List Operations

Providing an operation to list available operations for specific FDO types is strongly RECOMMENDED.
