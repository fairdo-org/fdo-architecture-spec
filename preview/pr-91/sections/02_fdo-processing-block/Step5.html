[S-5]: FDO Types Inspection

This step determines whether the given FDO types are as the client expects while processing the FDO. It assumes that was completed and that its status indicates that a 0.FDO/Type field is present (i.e., COMPLETE, TYPE_ONLY, PROFILE_MISSING, or DATA_MISSING).

There are many reasons to perform this step. It could be that the client software is only capable of processing limited types of information and the quicker it can determine whether the FDO is appropriate the better. Also, the accessing client may determine when to check for the FDO types as it could be using different hints to determine whether the FDO is appropriate.

Inputs
  • an FDO record: This step expects exactly one well-structured FDO record. Typically, this is the output of .
  • expected_fdo_type_list: A list of types that the client is looking for. It can be empty indicating that any FDO types within the FDO record will be accepted. This forces the ACCEPT_ANY flag described below.
  • A matching flag:
    • ACCEPT_ANY: Any FDO type is acceptable. This ignores the expected_fdo_type_list if provided.
    • EXACT_MATCH: Every FDO type in the FDO record must match any of the FDO types in the expected_fdo_type_list.
    • DERIVED_MATCH: The FDO types can be derived from the FDO types found in the expected_fdo_type_list. Derived types are backward compatible with their parent types.
Outputs
This step returns
  • status: FULL_MATCH, ALL_MATCH, PARTIAL_MATCH, DERIVED_MATCH, or NO_MATCH. For details, see the expected behaviour below.
  • type_matching: a list of the FDO types that match or are derived from the expected types. If the list is empty, it indicates that none were found. The client can determine from the number of FDO type matches whether the match is full or partial.
Expected behavior
In this step, the client will compare the list of FDO types in the FDO record with the expected_fdo_type_list looking for matches. As the 0.FDO/Type attribute uses attribute referencing, the client does not only inspect the 0.FDO/Type attributes alone but also the attribute which 0.FDO/Type is referencing. Comparisons are made between the expected_fdo_type_list and the value of the referenced attributes in the record. The following lists the possible scenarios:
  1. If the expected_fdo_type_list is empty and/or the matching flag is set to ACCEPT_ANY, all the FDO types within the FDO record are considered appropriate. The result is FULL_MATCH and the list of all FDO types found in the FDO record.
  2. The FDO types in the FDO record fully match those in the expected_fdo_type_list. The result is ALL_MATCH and the list of all matched FDO types.
  3. At least one of the FDO types in the FDO record matches at least one of the FDO types in the expected_fdo_type_list. The result is PARTIAL_MATCH and the list of the matching FDO types.
  4. The FDO types in the FDO record match none of the expected_fdo_type_list. There are two different results depending on the matching condition.
    • If the matching is set to EXACT_MATCH, the client concludes that the FDO does not have the proper type. The result is NO_MATCH.
    • If the matching is set to DERIVED_MATCH, the client will respectively analyze each of the FDO types in the FDO record and determine if they are derived from types that are within the expected_fdo_type_list. The assumption is that derived FDO types are compatible with their parent FDO types. To do so, the client resolves each of the FDO types into their respective FDO records and then analyzes these to see if the types they describe are derived from FDO types that match a type within the expected_fdo_type_list. If the client determines that one or more of the FDO types in the FDO records are derived from FDO types that are in the expected_fdo_type_list, it will conclude that the FDO record is compatible with one or more of its expected FDO types. The results can be
      • NO_MATCH if no derived FDO types are found.
      • DERIVED_MATCH if one or more derived FDO types matches are found.

This example shows a simple FDO record 10.1234/456 with two FDO types 0.example/Concept (the general type of resource) and 0.example/application-json-ld (the MIME type of the resource). Adding to the example is the fact that the FDO type 0.example/application-json-ld is derived from the FDO type 0.example/application-json.

Applying the processing step delivers
  • FULL_MATCH for an empty expected_fdo_type_list
  • ALL_MATCH for the expected_fdo_type_list [0.example/Concept, 0.example/application-json-ld]
  • PARTIAL_MATCH for the expected_fdo_type_list [0.example/Dataset, 0.example/application-json-ld]
  • NO_MATCH for the expected_fdo_type_list [0.example/application-json], but DERIVED_MATCH if the matching is set to DERIVED_MATCH
