FDO Attribute Definitions

This section is normative.

[R-Attr-1] Attribute Definitions are FDOs

FDO attribute definitions (short: attribute definitions) are themselves FDOs. Hence, they are unambiguously identified by a PID that resolves into an FDO record consisting of attributes. An attribute definition defines the semantics and the value space of its instantiating attributes in all FDO records it is instantiated in.

[R-Attr-2] Semantics of Attribute Definitions

Attribute definitions describe the semantics of an attribute using the 0.FDO/Name and 0.FDO/Description attributes. They MUST provide at least one localized and human-readable name for the attribute. For better understanding, at least one localized and human-readable description SHOULD be provided. Other information MAY be included in the attribute definition FDO records to refer to external resources and provide additional context for the semantics of the attribute.

[R-Attr-3] Cardinality of Attribute Definitions

An attribute definition MUST specify the cardinality of an attribute using the 0.FDO/Cardinality attribute. The cardinality defines how often this attribute is allowed to be instantiated in any FDO record. The cardinality MUST follow this regular expression: 
^(\d+)(\.\.(\d+|\*))?$
Examples for possible cardinalities include but are not limited to:
  • 1 (mandatory),
  • 0..1 (optional),
  • 1..* (mandatory and repeatable),
  • 0..* (optional and repeatable),
  • 2..3 (MUST occur two to three times).

The FDO attribute definition profile defines a set of attribute definitions that MUST be instantiated in the FDO record of every attribute definition. The FDO attribute definition profile is a profile that instantiates 0.FDO/ProfileDef and extends from the root profile. [R-Attr-5] Attribute Validation Mechanisms

An attribute definition MAY specify validation rules on the value of any attributes instantiating the attribute definition. This specification defines five different attribute validation mechanisms that MAY be used to define such validation rules.

Each attribute validation mechanisms requires different attributes in its attribute definition record to denote those validation rules. Hence, each of these mechanisms uses its own FDO profile. [R-Attr-6] Combining Attribute Validation Mechanisms

An attribute definition MAY use several attribute validation mechanisms at the same time. In this case, the attribute definition MUST contain the profiles of all the mechanisms that are used. The 0.FDO/ValidationStrategyForCombination attribute details how validation in such cases MUST be performed: If the value is anyof, this means that at least one attribute validation mechanism MUST apply, while allof means that all attribute validation mechanism MUST apply. The default is allof.

[R-Attr-7] Additional Attributes in Attribute Definitions

Attribute definition records MAY have additional attributes and instantiate additional profiles for any reason. This SHOULD be used to relate attribute definitions to existing external resources such as vocabularies, ontologies, or terminologies.

[R-Attr-8] Type System Attribute Definitions

All attribute definitions in this specification that use the 0.FDO prefix are part of the FDO type system. They are defined by the FDO Forum and implemented as handles within the Data Type Registry (DTR). These attribute definitions MUST be either reused by FDO implementations, or be mapped to corresponding attribute definitions or similar concepts using another technology (see ). This ensures interoperability between different FDO implementations and compliance with the type system.

[R-Attr-9] Community Attribute Definitions

Communities of practice MAY implement community-defined attribute definitions in the DTR or any other suitable open registry [[!RDA-DTR-WG]]. Special rules apply in case attribute definitions are updated, see – .
There are three qualitative categories of attributes (or attribute definitions): mandatory, type system, and community attributes.
  • mandatory attributes: The FDO Forum defines a set of mandatory attributes that MUST be used in each FDO record. This set is defined in the root profile and contains: 0.FDO/Type, 0.FDO/Profile, and 0.FDO/Data.
  • FDO type system attributes: The FDO Forum defines a set of attributes that are needed for the functioning of the FDO type system.
  • community attributes: Community-defined attributes are any attributes that are defined by a community of practice (i.e., usually not the FDO Forum). Interoperability between different communities and their attributes can be facilitated by either reusing attributes with their semantic meaning in other communities, defining more generic attributes, or by providing a bidirectional mapping process. They appear in different forms, with decreasing level of machine-actionability in the following enumeration:
    • attribute definitions: A community attribute may be specified as an attribute definition according to the rules in this chapter, against which the instantiated attribute in an FDO record must be validated.
    • reusing existing vocabularies, terminologies or ontologies: Community attributes may be implemented by referencing existing elements in vocabularies, terminologies, or ontologies. Validation may be performed, but is not guaranteed. See for more details.
    • labels: Community attributes may be used in records by a simple human-readable label. No validation can be performed here.

These categories of attributes do not impose additional requirements but help repositories and users to assess validation behavior, interoperability, and long-term interpretability of FDO records.
