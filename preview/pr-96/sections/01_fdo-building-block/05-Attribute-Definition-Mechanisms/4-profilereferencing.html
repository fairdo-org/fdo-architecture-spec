[R-Attr-13] Profile Referencing

Profile referencing permits an attribute definition to specify that the value (of an attribute instantiating this attribute definition) MUST be a reference to an FDO following a profile from a set of allowed profiles P1,...,Pn, n≥0. Depending on how many profiles are allowed, the referenced entity MUST be one of:

  • (n=0) an FDO (i.e., complying with the root profile),
  • (n=1) an FDO complying with a specific profile P1,
  • (n>1) an FDO complying with at least one of the P1,...,Pn.

To register an attribute definition that uses profile referencing with the allowed profiles P1,...,Pn, the following requirements MUST be fulfilled:

  • The attribute definition record MUST use the profile 0.FDO/AttributeDefProfileRef (that is, it contains the attribute (0.FDO/Profile, 0.FDO/AttributeDefProfileRef)). This indicates that the attribute definition applies the profile referencing mechanism.
  • The attribute definition record MUST contain the attributes (0.FDO/AllowedProfileInProfileRef, PID of Pi) for i=1,...,n, to indicate which profiles are allowed, see also Table 7. If n=0, this requirement does not apply.
When the attribute definition is instantiated, the value MUST be either a reference to another FDO following at least one of the specified profiles (where resolution MUST be possible in a reasonable amount of time), or an inline serialization of an FDO that instantiates at least one of the specified profiles.

The 0.FDO/Profile attribute uses profile referencing to ensure that the value of this attribute is a reference to an FDO profile (i.e., complies to 0.FDO/ProfileDef). Its attribute definition record is given on the left hand side in the image, and an instantiation of this attribute definition is given in the data FDO in the middle.
References are key to FDOs as they are used to associate bit-sequences and refer to any other related objects and information. The primitive data type for all references is assumed to be a string. However, their syntax, interpretation, and resolution remain implementation specific. This note aims to classify references into two categories depending on their degree of validation.
  • unvalidated references: A reference is considered an unvalidated reference if it is a string that follows the syntactic format of a PID. The PID may not be resolvable. The classification as an unvalidated reference may be performed by a heuristic that creates false positives. Therefore, unvalidated references may be called a PID candidate, as they syntactically appear to be a PID, but may not always resolve to an FDO.
  • validated references: For a reference to be considered a validated reference, it must resolve to a valid FDO record in reasonable time. It must also qualify as an unvalidated reference.
Profile referencing assumes that the reference to the FDO (that complies to one of the given profiles) is a validated reference.
