[S-5]: FDO Type(s) Inspection

This step determines whether the given FDO types are as the client expects while processing the FDO. It assumes that was completed and that its status indicates that a 0.FDO/Type field is present.

There are many reasons to perform this step. It could be that the client software is only capable of processing limited types of information and the quicker it can determine whether the FDO is appropriate the better. Also, the accessing client MAY determine when to check for the FDO types as it could be using different hints to determine whether the FDO is appropriate.

Inputs
This step expects that had a FDO root profile validation status of COMPLETE, REQUIRED_FIELDS, TYPE_ONLY and two inputs:
  • The list of types that the client is looking for. This is called the Expected_Fdo_Type_List. It can be empty indicating that any FDO types within the FDO record will be accepted. This forces the MATCH_ALL flag described below.
  • The Type_Matching flag. There are three possible values for this flag:
    • MATCH_ALL. Indicates that any FDO type is acceptable. This ignores the Expected_Fdo_Type_List if provided.
    • EXACT_MATCH. Indicates that the FDO types in the FDO record need to match exactly the FDO types in the Expected_Fdo_Type_List.
    • DERIVED_MATCH. Indicates that the FDO types can be derived from the FDO types found in the Expected_Fdo_Type_List. Derived types are backward compatible with their parent types.
Outputs
This step returns
  • the Type_Matching_Status: FULL_MATCH, ALL_MATCH, PARTIAL_MATCH, DERIVED_MATCH, or NO_MATCH
  • a list of the FDO types that match or are derived from the expected types. If the list is empty, it indicates that none were found. The client can determine from the number of FDO type matches whether the match is full or partial.
Expected behavior
In this step, the client will compare the list of FDO types in the FDO record with the Expected_Fdo_Type_List looking for matches. As the 0.FDO/Type attribute uses attribute referencing, the client does not only inspect the 0.FDO/Type attributes alone but also the attribute which 0.FDO/Type is referencing. Comparisons are made between the Expected_Fdo_Type_List and the value of the referenced attributes in the record. The following lists the possible scenarios:
  1. If the Expected_Fdo_Type_List is empty and/or the Type_Matching flag is set to MATCH_ALL, all the FDO types within the FDO record are considered appropriate. The result is FULL_MATCH and the list of all FDO types found in the FDO record.
  2. The FDO types in the FDO record fully match those in the Expected_Fdo_Type_List. The result is ALL_MATCH and the list of all matched FDO types.
  3. At least one of the FDO types in the FDO record matches at least one of the FDO types in the Expected_Fdo_Type_List. The result is PARTIAL_MATCH and the list of the matching FDO types.
  4. The FDO types in the FDO record match none of the Expected_Fdo_Type_List. There are two different results depending on the matching condition.
    • If the Type_Matching is set to EXACT_MATCH, the client concludes that the FDO does not have the proper type. The result is NO_MATCH.
    • If the Type_Matching is set to DERIVED_MATCH, the client will respectively analyze each of the FDO types in the FDO record and determine if they are derived from types that are within the Expected_Fdo_Type_List. The assumption is that derived FDO types are compatible with their parent FDO types. To do so, the client resolves each of the FDO types into their respective FDO records and then analyzes these to see if the types they describe are derived from FDO types that match a type within the Expected_Fdo_Type_List. If the client determines that one or more of the FDO types in the FDO records are derived from FDO types that are in the Expected_Fdo_Type_List, it will conclude that the FDO record is compatible with one or more of its expected FDO types. The results can be
      • NO_MATCH if no derived FDO types are found.
      • DERIVED_MATCH if one or more derived FDO types matches are found.

This example shows a simple FDO record 10.1234/456 with two FDO types 0.example/Concept (the general type of resource) and 0.example/application-json-ld (the MIME type of the resource). Adding to the example is the fact that the FDO type 0.example/application-json-ld is derived from the FDO type 0.example/application-json.

Applying the processing step delivers
  • FULL_MATCH for an empty Expected_Fdo_Type_List
  • ALL_MATCH for the Expected_Fdo_Type_List [0.example/Concept, 0.example/application-json-ld]
  • PARTIAL_MATCH for the Expected_Fdo_Type_List [0.example/Dataset, 0.example/application-json-ld]
  • NO_MATCH for the Expected_Fdo_Type_List [0.example/application-json], but DERIVED_MATCH if the Type_Matching is set to DERIVED_MATCH
