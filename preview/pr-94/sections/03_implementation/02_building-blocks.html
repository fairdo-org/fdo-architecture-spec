Attribute Mapping

[I2-1] Map type system attributes (M)
The FDO specification defines attributes that build up a type system. Each implementation either has to say that it uses these attributes directly (i.e., that it uses the handle-based implementation of the type system), or it accounts for how the type system is resembled using a different technology. The latter means to map the attributes from the type system to real attributes using the desired implementation. If no new community attributes or profiles should be defined by the given FDO implementation, then it is enough to map 0.FDO/Type, 0.FDO/Profile, and 0.FDO/Data, and 0.FDO/Metadata. If new community attributes or profiles should be defined, the relevant parts of the type system must be mapped. The complete type system can be found on Github.
[I2-2] Define other attributes (O)
Here you can define other attributes that are frequently used by your implementation.

[I3-2] Map implementation structure → FDO record (M)

FDO Attribute Definitions

[I5-1] Representation of FDO attribute definitions (M)
Each attribute definition is itself an FDO. You MUST specify how an attribute definition is represented in the given implementation (i.e., how the attribute definition looks like; this can be understood as a recipe for building FDO attribute definitions in the given FDO implementation).
Note: [I5-1] defines the overall structure of an attribute definition. You can go into more detail of how to encode syntax, semantics, complex attributes, and complex validation rules in [I5-3] – [I5-8]. If your implementation uses additional implementation-specific rules for attributes or validation, you can describe them in [I5-9] - ...
[I5-2] Attribute Definition Profile (M)
Give the PID for the attribute definition profile that is used in your implementation.
[I5-3] Encoding Semantics (M)
Specify where one can find the name, the description, and cardinality of an attribute definition.
[I5-4] Encoding Syntax (R)
Specify how the following syntax rules are represented in an attribute definition in the given implementation. An attribute…
  • … follows one of the primitive data types “string”, “number”, “integer” and “boolean”.
  • … complies with a regular expression.
  • … lies within a numeric range.
  • … is equal to one element from a whitelist.
  • … is not equal to all elements from a blacklist.
Note: If some of these rules are not compatible with the given implementation (i.e., cannot be encoded in the given technology), please point this out. Different technologies MAY have different levels of expressibility.
[I5-5] Inline Combinations of Attribute Definitions (R)
Specify how inline combinations of attributes are represented in the given implementation.
[I5-6] Unions of Attribute Definitions (R)
Specify how unions of attributes are represented in the given implementation.
[I5-7] Profile Referencing (R)
Specify how profile referencing looks like in the given implementation.
[I5-8] Attribute Referencing (R)
Specify how attribute referencing looks like in the given implementation.
[I5-9] – ... Implementation-specific rules (O)
You can further specify semantic, syntactic, and complex validation rules that are not covered by this document. Then, you MUST describe how the rules are encoded in the given implementation, and how a record is validated against the rules.
