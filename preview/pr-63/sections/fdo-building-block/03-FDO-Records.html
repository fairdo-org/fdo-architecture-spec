Each FDO Record MUST fulfill the following requirements:

An FDO Record consists of tuples (called “FDO Attribute”):
[R3-1]
A PID identifying an FDO resolves into a structured information record, called the FDO Record.
[R3-2]
The FDO Record consists of a finite number of n-tuples with n>1 (called FDO attributes, short: attributes) that can be interpreted by a machine. The limit for the number of tuples per record depends on the implementation. Each can always be unambiguously mapped onto a canonical triple form (subject, predicate, object) — regardless of whether the implementation uses 2, 3 or more elements. The subject is optional and has the FDO’s own PID as defined default.
  • The predicate MUST be either a PID that resolves to an attribute definition or a human-readable name.
  • The object may be any literal; if the predicate refers to an attribute definition, the object MUST be validated against it.
  • The subject is OPTIONAL. If the subject is omitted, the subject is assumed to be the PID implicitly
  • Elements of higher level tuples are OPTIONAL and may contain additional meta-information about the statement itself that is not relevant to validation
  • [R5-2a] Every n-tuple MUST be projectable onto a canonical triple form: π(a)=(s, p, v) This projection forms the basis for validation (3.8), RDF mapping (3.12) and all further processing steps that require a fixed statement structure.
  • [R5-2b] The cardinality rules of an attribute definition (see [R5-7]) always refer exclusively to the predicate p — regardless of the chosen arity n. A predicate with cardinality 1..* permits any number of tuple instances, whether realised as a pair, a triple or a higher-order tuple.
  • [R5-2c] Implementations that use only the 2-tuple (ordered pair) are considered to be minimally compliant. Implementations that use the subject position (n=3) or qualifier positions (n>3) MUST explicitly indicate this via the attribute definition (see [R5-2d]).
  • [R5-2d] An attribute definition MUST declare the arity it permits, using the attribute 0.FDO/ArityMode with one of the following values:
    • PAIR_ONLY (only n=2, subject implicit),
    • TRIPLE_ALLOWED (n=2 or n=3, explicit subject permitted),
    • QUALIFIED (n≥2, additional qualifier positions permitted).
    If 0.FDO/ArityMode is omitted, the default PAIR_ONLY applies — this ensures that all existing attribute definitions remain automatically backwards-compatible without requiring any changes.
An FDO Record contains the attributes 0.FDO/Type, 0.FDO/Profile and 0.FDO/Data:
[R3-3]
Each FDO Record MUST link to at least one FDO Profile, which it complies to, via the designated attribute 0.FDO/Profile in its FDO Record. To link multiple FDO profiles, the attribute 0.FDO/Profile MAY be repeated multiple times in the FDO Record.
  • The first element of such a tuple representing the FDO’s profile is either the PID 0.FDO/Profile , or the string FDO_Profile.
  • The second element is a PID referencing an FDO profile.
[R3-4]
Each FDO MUST specify its FDO type via the designated attribute 0.FDO/Type in its FDO Record. To link multiple FDO types, the attribute 0.FDO/Type MAY be repeated multiple times in the FDO Record.
  • The first element of such a tuple representing the FDO’s type is either the PID 0.FDO/Type , or the string FDO_Type.
  • The 0.FDO/Type attribute follows the attribute referencing mechanism as defined in .
[R3-5]
Each FDO MUST contain the designated attribute 0.FDO/Data in its FDO Record at least once. The 0.FDO/Data attribute points to data associated with the FDO.
  • The first element of such a tuple representing the FDO’s data is either the PID 0.FDO/Data , or the string FDO_Data.
  • The 0.FDO/Data attribute follows the attribute referencing mechanism as defined in .
