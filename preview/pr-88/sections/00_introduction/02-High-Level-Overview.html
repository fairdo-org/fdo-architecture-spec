Overview

In order to enable automated processing regardless of the technology used, FDO implementations must comply with this document. This document specifies especially implementation-agnostic rules, the FDO structure, and FDO components.

The main principle of FDOs is simple: a record contains a flat list of attributes. Each attribute has two parts: a PID to an attribute definition, and a value. The PID may be resolved for detailed information about semantics and structure of the value (e.g. validation). The value may be used as the client intents, considering the attributes semantics. While the specification provides mandatory and optional attributes, Communities of Practice are free to register their own in open, defined registries. FDO Profiles are comparable to schemas: They determine the attributes for FDOs. As multiple Profiles can be used by an FDO, this allows for flexible reuse of profiles, if their scope fits the resource and available information. Profiles may be useful for clients, for validation, and for guidance/harmonization.

Section 5 defines the essential components and rules needed for creating and interpreting FDOs and the FDO type system. All components, as shown in [[[#fig1]]], are themselves fully valid FDOs without any special mechanisms. This grounds FDOs in themselves to prevent unwanted dependencies from specific technologies and enable a common exchange format between implementations.

In Section 6 we describe how a client finds, accesses, and interprets FDOs to get to the data represented by it. We expect that implementations of FDOs will vary and MAY not realize all the building blocks. Thus, we specify in Section 7 how implementations adopt this document to facilitate interoperability between implementations.

In the following, we define a few basic terms the specification uses and concepts that influenced the specification.

  • Binding/Bundling: FDO components are linked to each other using persistent identifiers, which can be considered a binding or a bundle. Implementations may also choose to store, for example, the record, within the same system as the PID to form a tighter kind of binding / bundling. Core for these bindings are globally unique and resolvable persistent identifiers that resolve into well-defined structures.
  • Encapsulation: Encapsulation in Object-oriented programming means wrapping internal structures by methods enabling information hiding. For FDOs it describes the integration of operations with FDOs, i.e., to use operations to access content without the need to know the internal structure of the FDO. Thus, FDOs can support encapsulation on all levels of the FDOs layered structure.
  • Machine Actionability: Machine actionability means that clients can not only read structures and identify elements, but can also infer which actions can be taken without human intervention. This requires the accessibility of FDO profiles, the definition of FDO attributes and the association with operations. Machine actionability requires machine interpretability. For details see [[MachineActionability]].
  • Machine Interpretability: Machine interpretable means that clients are able to structurally identify elements and relate them with semantic artifacts in a given context and therefore associate a defined purpose. Machine interpretability requires machine readability. For details see [[MachineActionability]].
  • Machine Readability: Machine readable means that elements can be identified by clients with high or absolute certainty based on precisely structured data. For details see [[MachineActionability]].
  • Metadata: Metadata is data describing data. In the context of FDOs metadata occurs in general at two layers: (1) FDO attributes as part of the FDO record and (2) the rich metadata description as provided by the data creator, e.g., within repositories, associated with the data.
    Metadata describes properties of the bit-sequence(s) of an FDO to make them FAIR. FDO attributes enable machines to interpret values in FDOs. Metadata can be of different types such as descriptive, deep scientific, provenance, rights, access permissions, transactions, etc. Usage of these terms has not been harmonized yet.
  • Mutability: Data providers need to make clear policy statements whether the content of a bit-sequence that is encapsulated in an FDO is immutable or mutable, i.e., changing over time such as is often the case in databases. Inspecting the correctness of these statements SHOULD be part of auditing procedures.
  • Resource: Each FDO is a bundle that encapsulates, represents, and describes a resource. It could be a digital resource, in which case the resource would usually be a data bit-sequence. A bit-sequence can be any form of digitalized information representable in an array of bits. But it is also possible that this resource is physical, in which case there is no data bit-sequence attached to the FDO. The resource is the heart of the FDO and all other components are there to make the resource and its metadata machine actionable.
